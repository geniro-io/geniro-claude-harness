# EXP-008: does telling the planner to state checkable predicates and cite everything change how grounded its spec is?

- **Module:** none — this does NOT use `loop.sh`. The unit is a spec, not a
  review, and the oracle is `check-claims.py` plus hand adjudication, not a
  judge subagent. Do not compare its numbers to any module run.
- **Status:** landed (measurement recorded; no skill change proposed)
- **Failure pattern:** the opposite of one. Four specs written for real
  SWE-bench Verified tasks (`pydata__xarray-3993`, `pytest-dev__pytest-10356`,
  `pylint-dev__pylint-8898`, `sphinx-doc__sphinx-8548`) emitted 187 citations
  and every one resolved; ~11 hand-adjudicated substantive claims were all
  true. That hunt was for planner defects and found none — but the planner
  prompt carried the grounding discipline shipped in `3151bb3` (Phase 3's
  assumption ledger: "one checkable predicate per branch"), so it measured the
  post-fix planner. This experiment removes that one paragraph and re-runs.
- **Change (ONE thing):** the planner prompt's grounding paragraph. Arm A
  (control, already run) contains:

  > Section 4 (Assumptions) must state checkable predicates about the code or
  > environment — facts a reader could confirm or refute by opening the repo —
  > not vague framing. Cite files with `path/to/file.py:LINE` wherever you
  > assert something about existing code, in Assumptions, Steps, and Risks
  > alike. Aim for 6-12 claims about the codebase across the document.

  Arm B deletes exactly that paragraph. Same four tasks, same repos at the same
  `base_commit`, same template, same "no extra verification pass" constraint,
  fresh subagents.

- **Metrics.** A rate would reward arm B for staying quiet, so the primary
  metric counts what goes unchecked, not what goes wrong:
  1. `uncited_factual_bullets` — bullets in §4/§5/§6 that assert something
     about existing code and carry no `path:line`. **Primary.** An unwritten
     assumption is invisible to every gate downstream, which is the failure the
     user reported; a wrong citation at least gets checked.
  2. `citations_emitted` and `citations_resolving` — absolute counts, mechanical.
  3. `false_claims` — substantive claims hand-adjudicated wrong. The payload.

- **Prediction (written before the run):** arm B emits materially fewer
  citations and a materially higher share of uncited factual bullets in
  §4/§5/§6, and produces at least one substantive false claim across the four
  specs where arm A produced zero.

- **Success gate:** a difference visible without statistics at n=4 — roughly
  2× on uncited factual bullets, or any false claim in arm B against arm A's
  zero. Anything smaller is not resolvable at this n and is recorded as
  inconclusive, not as a win.

- **What a null result would mean:** if arm B is also clean, the shipped
  instruction does nothing measurable on tasks of this shape, and the
  always-on Phase 7.5 gate is carrying the improvement alone. That is a
  publishable outcome for this repo, not a failure — it would redirect effort
  away from prompt wording and toward the gate.

## Runs

| stage | run dir / ledger line | verdict |
|---|---|---|
| arm A (control, grounding paragraph present) | `scratch/swe/*/spec.md` | 187 citations, **187 resolve**, 0 ambiguous, 0 bad; bullets 103, uncited **10 (9.7%)**; 0 false claims |
| arm B (paragraph removed) | `scratch/swe-b/*/spec.md` | 142 citations, 123 resolve, **19 ambiguous**, 0 bad; bullets 89, uncited **23 (25.8%)**; 0 false claims |

Per task — citations / resolve / ambiguous | bullets / uncited:

| task | arm A | arm B |
|---|---|---|
| xarray-3993 | 49 / 49 / 0 \| 27 / 2 | 41 / 41 / 0 \| 18 / 1 |
| pytest-10356 | 39 / 39 / 0 \| 24 / 3 | 31 / 31 / 0 \| 23 / 6 |
| pylint-8898 | 52 / 52 / 0 \| 27 / 3 | 26 / 26 / 0 \| 26 / **14** |
| sphinx-8548 | 47 / 47 / 0 \| 25 / 2 | 44 / 25 / **19** \| 22 / 2 |

"Ambiguous" = a bare basename (`__init__.py:1595`) whose directory is carried
only by document context. Not a false claim; a citation a reader cannot resolve
without holding the whole spec in their head. Arm A produced none.

~20 substantive claims were hand-adjudicated across the eight specs — mypy
config, `pytest.warns` line contents, MRO ordering, the only writer of
`pytestmark`, five options through one splitter, Python regex semantics, a bare
checkout's missing `astroid`. **Every one was true, in both arms.**

## Decision

**Half the prediction held, and the half that failed is the more interesting
one.** Arm B emitted 24% fewer citations and left 2.7× the share of §4/§5/§6
bullets ungrounded (25.8% vs 9.7%) — past the pre-registered 2× gate. It also
produced 19 citations a reader cannot resolve, against arm A's zero, which was
not predicted at all. But the second gate — at least one substantive false
claim against arm A's zero — was **not** met: both arms are clean on every fact
that can be checked.

**So the instruction does not make the planner more accurate. It makes the
planner more checkable.** That distinction is the finding. Arm B's 23 uncited
bullets and 19 ambiguous citations are 42 pieces of reasoning Phase 7.5 cannot
touch, because spec-challenge can only refute a claim that was written down
with a pointer to the code. An unwritten assumption is not wrong — it is
invisible, and `/geniro:implement` is then the first thing that touches reality.
That is a better account of the reported failure ("the plan turns out to be
wrong") than "the planner asserts false facts", for which this experiment found
no evidence at all.

Both shipped changes are supported, by a mechanism other than the one
predicted: Phase 3's assumption ledger converts silent premises into written
predicates, and always-on Phase 7.5 is what then reads them back against the
code. Neither is a fix for inaccuracy that was not there.

**Limits, and they are real.** n=4, one trial per arm, no statistics. The
grounding gap is task-dependent — pylint drove it (14/26 uncited) while xarray
showed none. Zero false claims in either arm means this benchmark cannot resolve
accuracy effects **at all** at this difficulty; the tasks are too well specified
for a capable planner to get facts wrong. Chasing accuracy on SWE-bench-shaped
tasks is a closed road; measuring *coverage of checkable claims* is the open one.

**Five instrument bugs, all caught before either arm was judged, and every one
over-counted arm B's defects** — the arm the hypothesis predicted would look
worse. Missing `.rst` in the citation pattern; a symbol-presence check that was
wrong 6 times out of 6; root-level files (`setup.cfg`) classed as ambiguous; a
resolver that invented directories and reported two real files as out-of-range
spec defects; and bare-basename resolution finally narrowed to same-line,
same-basename only. The instrument, not the model, was the hard part of this
experiment, and the failure mode was always confirmation of the author's
prediction. `check-claims.py` ships with the five planted fixtures as its
regression suite for exactly that reason.
