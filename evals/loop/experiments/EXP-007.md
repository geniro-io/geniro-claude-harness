# EXP-007: A-vs-A — does the spec-check stand measure signal or noise?

- **Module:** spec-check
- **Status:** landed (stand calibration, no skill change)
- **Failure pattern:** n/a — this is the mandatory first run on a new benchmark
  (DESIGN.md §A-vs-A). Champion against champion must come back a tie; the CI
  width is the noise floor every later verdict on this module is read against.
- **Change (ONE thing):** none. Both arms are `variants/champion`, same prompts,
  fresh executor subagents per arm (no cache replay between them).
- **Prediction:** exact recall tie; some noise spread, since the flagged set
  beyond the rubric is where run-to-run variance lives.
- **Success gate:** recall delta indistinguishable from zero. A significant
  difference would mean the stand cannot separate a real effect from run noise
  and must not be used until it can.

## Setup

- Executor: Claude subagents (`adapters/claude-subagent.md` §Executor protocol).
  This is the faithful choice, not the cheap one — production spec-challenge
  spawns Claude verifiers, so a composer-2.5 sweep would measure a configuration
  nobody runs. Free on subscription; no spend approval was needed or sought.
- Judges: 12 blind Claude subagents, one per trial, each reading only its own
  `judge-prompt.txt`.
- Benchmark: 6 dev (5 positive, 11 must-find items + 1 negative), rubric v1.

## Decision

The stand separates signal from noise on recall and is usable. Two bounds to
carry into every later verdict on this module:

1. **The recall MDE of 0 is not infinite sensitivity — it is coarseness.** Four
   of five positive tasks scored 1.0 in both arms, so the per-task deltas had
   nowhere to land. The suite is near the saturation DESIGN.md §6 warns about,
   and a recall win on it would have to come from the one task that is not
   saturated. Treat recall here as a floor check, not a fine instrument, until
   the benchmark grows harder tasks. GROWN in 1be84e2: the dev set is now 10
   tasks, 4 of them real (see EXP-008). These numbers describe the 6-task set
   and are not comparable to any later run.
2. **The noise floor is 0.33 findings/task.** A future variant moving noise by
   less than that is reporting run-to-run variance.

## The reproducible miss was the fixture, not the run

Both arms failed `planted-5` `gt-2`, and both were right to. The rubric asserted
that a `legacy-ledger-read` entry at `percentage: 100` meant the flag carried
live traffic — but nothing in the tree read that flag. `src/ledger.ts` gated only
on `unified-ledger`, and `flag()` was a constant-false stub, so the rollout
config was inert and "now-unused" was true as written. Both arms cited the
rubric's own lines, concluded the entry was already unreferenced, and both judges
independently bucketed that correct finding as **noise**. The right answer cost
recall and precision at once.

No EXP-008 against a blind spot that does not exist. The fixture was repaired
instead: `flag()` resolves against `deploy/rollout.yaml` through a per-request
cohort and bucket, the legacy read is gated on `legacy-ledger-read`, and rubric
**v2** names the call site. Re-swept, 2 independent trials, champion unchanged —
`recall_must` 1.0 in both, `pass` in both, and the judges match `gt-2` on the
call site (`"read live at src/ledger.ts:5 — it is the path that actually serves
reads today"`). The stub artifact went with it: no trial now reports `flag()`
always returning false, because it no longer does.

**planted-5's v1 numbers above are void** — the rubric-version pin in
`compare.sh` refuses any comparison that crosses them, which is what it is for.
The other five tasks are untouched and still comparable.

## What is now mechanical

`contested_must` flags any missed must-find whose own lines a discarded finding
already cites, and `score.sh` prints it with a warning. "Looked in the right
place, disagreed with the ground truth" is the fingerprint of a wrong rubric, and
a scored run now says it out loud instead of leaving it for a transcript read to
notice. Scoring is untouched — it is a pointer, not a metric.

A second guard covers the cheaper failure: `tests/evals/spec-check-module.sh`
walks every dev fixture with a committed `tree/` and fails if a rubric item names
a file outside it, points past the end of one, or if a spec citation dangles
without a rubric item planting it. A task whose tree is fetched at stage time is
checked for the fields staging needs instead — offline it has nothing to resolve
against. Holdout is excluded on purpose: a failure message would print holdout
content into the tuning session.
