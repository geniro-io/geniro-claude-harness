# EXP-008: A-vs-A — does the partition stand measure signal or noise?

- **Module:** partition (new)
- **Status:** running (stand calibration, no skill change)
- **Failure pattern:** n/a — this is the mandatory first run on a new benchmark
  (DESIGN.md §A-vs-A). Champion against champion must come back a tie; the CI
  width is the noise floor every later verdict on this module is read against.
- **Change (ONE thing):** none. Both arms are `variants/champion`, same prompts,
  fresh executor subagents per arm (no cache replay between them).
- **Prediction:** exact recall tie. Noise spread is likelier here than on
  spec-check, because a partition run can name a coupling the rubric does not
  carry without being wrong — a real shared file the fixture author did not
  plant still reads as a finding.
- **Success gate:** recall delta indistinguishable from zero. A significant
  difference means the stand cannot separate a real effect from run noise and
  must not be used until it can.

## What this module measures

The Phase 2 file-set partition in `/geniro:implement`: given a fixed todo list
and the tree it will be applied to, decide which todos can be handed to separate
agents concurrently. The rubric's items are couplings that are genuinely present
and do not look it, so `recall_must` reads "did the partition catch the hidden
dependency" and `noise` reads "did it call independent work coupled".

Both directions cost something real, which is why the benchmark carries a
negative task: a missed coupling puts two delegates in one file with no locking
and last-write-wins; a phantom coupling collapses the partition to a single
group and delegation never fires at all.

## Setup

- **Executor: Claude subagents** (`adapters/claude-subagent.md` §Executor
  protocol), driven through the `mock` transport so the driver assembles the
  real prompts and `collect-subagent-results.sh` wraps the subagent output.
  This is the faithful choice, not the cheap one: the partition is computed by
  the `/geniro:implement` orchestrator itself, which runs at the session tier
  (`model: inherit`), so a composer-2.5 sweep would measure a configuration
  nobody runs. Free on subscription. The `adapter` field in `spec.json` records
  the transport (`mock`), not the brain — the model field carries that.
- **Judges:** blind Claude subagents, one per trial, each reading only its own
  `judge-prompt.txt`.
- **Benchmark:** 6 dev — 5 positive (9 must-find couplings) + 1 negative;
  4 synthetic trees + 2 staged from a real monorepo at a pinned commit. Coupling
  classes covered: shared public surface, in-flux contract, shared registry,
  ordered shared list, duplicate helper, file overlap, shared config.
  Rubric v1 throughout.
- **Cost note:** a probe on the paid path measured the two real-monorepo tasks
  at 1.28M tokens/call against 152K for a synthetic one — 8.4x. Recorded here
  because the naive whole-set extrapolation understated the sweep threefold, and
  any future paid run of this module must probe a REAL task, not a planted one.

## Decision

The stand is internally consistent — champion against champion ties exactly, and
the negative task came back clean from both arms, so the loop cannot optimize
itself toward overtriggering without that showing up. But the result that matters
is not the tie:

**The benchmark is saturated on the day it was built.** Every positive task
scored 1.0 in both arms, so the per-task deltas had nowhere to land, and the
recall MDE of 0 is coarseness, not sensitivity — the same bound EXP-007 recorded
for spec-check, arriving here immediately rather than after a few experiments.
As it stands this module can prove a variant did no HARM and cannot prove one
helped.

**What that says about the artifact under test.** The Phase 2 partition
instruction, executed at orchestrator tier, got every planted coupling on the
first pass — including both real-monorepo tasks, where the coupling had to be
discovered by reading an injectable registry and an Electron IPC contract rather
than by pattern-matching a barrel. Zero phantom couplings across 12 runs. The
partition step is not where this skill is weak, and a content experiment against
it would be measuring a saturated metric.

**Two bounds to carry into every later verdict on this module:**

1. **Recall here is a floor check, not an instrument** — it distinguishes a
   broken variant from a working one and nothing finer, until the benchmark
   carries tasks the champion actually fails.
2. **The noise floor is 0.00 findings/task on noise_strict, but plausible_real
   ranges 0.33-0.50/task and lives entirely on the real-repo tasks.** A future
   variant moving plausible_real by less than that is reporting run-to-run
   variance — and on a real tree, an unmatched finding is more often a rubric
   gap than a wrong answer.

## The rubric was incomplete, and both arms proved it

Every unmatched finding across both arms was bucketed `plausible-real`, never
`noise`. Read individually they are correct couplings the fixture author did not
plant:

- `real-1` — the exhaustive `Record<AgentKind, string>` binary-override map and
  the `AgentKind` union itself are additional shared write sites for two new
  adapters; a missing key there is a compile error, not a silent drop.
- `real-1` — the adapter provider array is also written by the third todo
  (per-adapter timing), coupling it to both new-adapter todos.
- `real-2` — the transcript screen container is the single holder of the list
  state and render loop, so the virtualization todo collides with the two IPC
  todos there.
- `planted-1` — the ledger is module-private, so the summary helper must be
  written into the same file the PDF renderer is added to. A real coupling the
  fixture created by accident.

None of these are scored as wins, because the rubric does not carry them. The
next edit to this module is to add them as ground-truth items (bumping every
touched rubric to v2, which invalidates these baseline runs), and to author tasks
whose couplings the champion misses — not to tune the preamble.

## Fixture defect found and worth fixing

`real-1`'s todo-4 describes the empty-state string as `"No runs"`; the tree at
the pinned commit reads `"No chats yet"`. It does not affect the rubric (todo-4
is separable under either wording) but a task that misdescribes its own tree
teaches the executor to distrust the task text.
