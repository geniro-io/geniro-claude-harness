# EXP-021: does folding the optimizations rubric into the architecture agent cost any findings?

- **Module:** review
- **Status:** screening
- **Framing — NON-INFERIORITY, not a win hunt.** The question is not "does merging
  help" (it cannot help recall) but "does one agent carrying both rubrics find what
  two agents carrying one each found". A tie PASSES and buys one fewer spawn per
  review. Only a recall loss fails it.
- **Failure pattern:** spawn count paid for rubric separation that the rubrics
  themselves do not claim. `optimizations-criteria.md` is 778 words, and its own
  §Scope boundary hands SIX of its concerns to architecture by name — N+1 queries,
  ORM eager-loading, architecture-level caching, missing pagination, sync I/O in
  async context, inefficient algorithms — leaving six micro-level categories on the
  changed lines. `architecture-criteria.md` already owns Performance & Scalability,
  which is where those six were routed. Two agents read the same changed files to
  apply two halves of one perf rubric.

  Measured on a production run (11 reviewers, PR-scale diff): the optimizations
  reviewer cost ~2.0M tokens across 26 tool uses and returned 2 findings, one
  MEDIUM and one LOW, both on code the architecture reviewer also read.
- **Change (ONE thing):** `facets.json` only — the `optimizations` facet is removed
  and `optimizations-criteria.md` is appended to the `architecture` facet's criteria
  list. **No criteria prose is edited**; the variant's `criteria/` is byte-identical
  to the champion's, verified by `diff -rq`. Seven facets become six.

  This is the shape the champion already ships for `conventions`, which carries
  three criteria files (`guidelines` + `conventions` + `rules-compliance`) in one
  spawn — so the merge is an existing pattern applied once more, not a new mechanism.
- **Why this design avoids the denominator trap:** dropping a dimension outright
  makes recall read 1.0 by construction, because the rubric's items leave the
  denominator with it. Here every `optimizations-criteria.md` item still ships, to a
  different agent, so a rubric item that stops being found registers as a real
  recall loss rather than vanishing from the measurement.
- **Prediction:** recall tie or within noise on `recall_must`; noise flat or slightly
  down (one fewer agent emitting near-duplicate perf observations on the same hunk);
  cost −14% per sweep (42 calls vs 49). The dev set is planted-defect-heavy and
  carries few perf-specific musts, so the most likely outcome is an exact tie on
  both axes — which is a PASS under the framing above.
- **Success gate:** `Δrecall_must` CI lower bound at or above zero (a tie passes;
  any confirmed loss fails and keeps the champion's seven facets). Noise must not
  rise above the module's recorded `noise_floor`. A recall loss traceable to a
  specific perf rubric item is the informative failure — record which item, since
  it names what the separate agent was actually buying.
- **Caveat (pre-registered):** a tie on this dev set is weak evidence for perf
  coverage specifically — the benchmark's musts are mostly correctness defects. If
  the screen passes, confirmation on holdout with a second model family is required
  before promotion, and the holdout set should be checked for at least one perf must
  before the result is read as covering this rubric at all. If it carries none, say
  so and treat the result as "no coverage loss detected on tasks that do not test
  this rubric" rather than as a pass on perf coverage.

## Result

**NOT PROMOTED, 2026-09-01.** Champion keeps its seven facets; `optimizations` stays
its own spawn.

| axis | variant (1 agent) | champion (2 agents) | Δ | CI95 | MDE |
|---|---:|---:|---:|---|---:|
| `recall_must` | 0.6667 | 0.7000 | **−0.033** | [−0.133, +0.067] | 0.100 |
| `noise` | 0.643 | 1.429 | **−0.786** | [−1.714, +0.071] | 0.893 |

Per-task recall: 1 win, 2 losses, 2 ties. Harness verdict: *"tie / inside CI — no
promotion (effects below the recall MDE of 0.1 are invisible at this n)."*

**The pre-registered gate is not met.** It required the `Δrecall_must` CI lower bound
at or above zero; it came back at −0.133. Both the gate and the harness say the same
thing, so the decision is unambiguous even though the reasons differ — the harness
calls it underpowered, the gate calls it unproven.

**The gate was badly written, and that is the more useful finding.** With MDE 0.100 the
CI half-width is ~0.10, so even a perfect zero-delta tie would land a lower bound near
−0.05 to −0.10. The gate could therefore only be met by a positive point estimate — it
was a superiority test wearing a non-inferiority label, unpassable by the very outcome
the framing called a PASS. A non-inferiority gate has to be stated against a margin the
design can actually resolve (e.g. "CI lower bound above −1 × MDE"), not against zero.

**What the numbers do say.** The point estimate leans against the merge: 3.3pp less
recall, losing on two tasks and winning on one. Noise more than halved — 0.64 vs 1.43
findings per task — which was predicted and is the honest upside of one agent instead
of two. Neither effect separates from zero at this n, and only 5 of the 7 dev tasks
carry must-finds at all (`planted-4` and `planted-neg-1` score `recall_must: null`), so
the recall comparison rests on five paired observations.

**Prediction accuracy:** the pre-registered call was "exact tie on both axes". Recall
came back directionally negative rather than flat, and noise moved substantially rather
than flat. Half right at best.

**Follow-up not opened.** Buying the resolution to separate a 3pp recall change from
zero means a materially larger benchmark, and the prize is roughly $1 per review run.
That is the wrong thing to spend benchmark growth on; the merge stays rejected on the
evidence available, and the two cheap verifiers that motivated it were already removed
by the pr-metadata LOW cap landing separately.

**One contested must** — `smoke-1` trial-1, `gt-2` matched to `F5` on the variant arm.
`finish` flagged it. Not re-adjudicated, because the verdict does not turn on it: even
scoring it fully in the variant's favour leaves the delta inside the CI.

### Void run, 2026-09-01 — `--facets` omitted

The first screen returned byte-identical finding counts on all 14 task-trial pairs.
That is not a tie; it is the signature of two identical configurations. `loop.sh screen`
runs the module's `screen_facets` subset from `target.json` — `["bugs", "security",
"tests", "regressions"]` — and **neither facet this experiment changes is in it**. The
variant's whole diff lives in `architecture` (which gains the optimizations criteria)
and in the removal of `optimizations`; with both filtered out, the two arms ran the same
four facets over the same tasks.

`loop.sh`'s own header says so — "Runs the module's `screen_facets` subset by default
(target.json); `--facets` overrides (an experiment adding its own facets needs that)" —
so the guard existed and was not read before launching.

Re-run pins the facets the change actually touches: `--facets architecture,optimizations`.
The arms are deliberately asymmetric there — champion runs two facets, the variant one —
because one agent replacing two IS the change under test. Scoring is per-trial union
against the same rubric, so the asymmetry is the measurement, not a confound.

**Generalizes past this experiment:** any variant whose change lives outside
`screen_facets` screens against itself and reports a tie. Identical per-task finding
counts across every pair is the tell — read it as a plumbing failure, never as
non-inferiority.
