# Canonical agent-loop invariants

The agent-loop invariants every Geniro orchestrator skill upholds, regardless of phase count. A skill cites this file and then adds its own skill-specific invariants (e.g. `/geniro:implement` adds subagent-delegation and single-`in_progress`-todo rules; `/geniro:review` adds the Reporter boundary). This is the single source — consuming skills reference it rather than restating the list.

1. **One result per tool call.** Every Edit / Write / Bash / Agent spawn produces exactly one structured result. A failed spawn yields a result with `status: failed` — never an absent one.
2. **Args validated before execution.** Bash commands built from `$ARGUMENTS` or state-file fields pass input sanity-checks; paths are absolute; slugs match the project's naming rules.
3. **Permission before side-effect.** Any tool call that mutates external state (`git push`, `gh pr create`, a posted PR comment, a tracker write) is preceded by an `AskUserQuestion` approval or a recorded prior approval.
4. **Bounded, structured tool results.** Subagent and Bash output is capped (truncate-with-marker, or summarize) before it reaches downstream reasoning, so a single large result can't crowd the orchestrator's context.
5. **Escalation gates, not silent abort.** Bounded retry loops surface to the user via `AskUserQuestion` at exhaustion — and earlier when the loop stops converging (no forward progress, the same failure recurring, or cost/scope drifting past the expected tier). Never a silent abort, never an infinite loop, never the full retry budget spent against an unmoving wall.
6. **Final answer grounded in observations.** A completion claim quotes actual tool output (a push ref, PR URL, commit SHA, test result) — never "it succeeded" without evidence. Read the state-file `## Tool log` before claiming a clean state.
7. **Errors, denials, cancellations, timeouts → structured observations.** A failed command, denied permission, hook-blocked write, subagent timeout, or non-zero exit becomes a structured observation entry — never silently skipped.
8. **Repo-state and defect-scope claims cite what was actually checked.** State what happened in history — a merge, a rebase, which option got picked — only from a source consulted this session (`git log`, `git reflog`, the run's own tool calls), and re-derive it before repeating it as settled fact rather than carrying the first plausible account forward. A symptom reproducing outside the diff shows only that the cause isn't in the diff — before calling it a shared defect, check whether the path is tracked (`git ls-files`, `.gitignore`); a regenerated or gitignored artifact differs locally for reasons the shared repo never sees.
9. **Scratch and probe files never land in the reviewed tree.** A throwaway file created to test something empirically goes under this run's own Geniro state directory for the task or branch, never inside the tree under review — a file left under `src/` sits inside the build/lint include and is one broad `git add` away from shipping, and cleanup keyed to turn completion does not cover a turn that aborts.

**Turn-completion check (deliberately un-numbered).** Before stopping and returning control to the user, re-read the last emitted paragraph. A statement of intent ("I'll now run X" / "Next I'll ask which option you prefer"), an announced-but-unfired `AskUserQuestion`, or a promise of work not yet done means the work happens now, with tool calls — fire the question, run the command, spawn the agent. Likewise a freshly-arrived tool result (including an answered question) is continued with the next action or a visible acknowledgment, never a silent stop. Stop only when the phase's deliverable is complete or the skill is blocked on an *answered* question it has actually asked. This guards a documented model failure mode: deep into long sessions, the model can end on a text-only statement of intent without issuing the corresponding tool call — recoverable interactively with "continue", but a silent stall in autonomous runs and at gates (gate instantiation: `${CLAUDE_PLUGIN_ROOT}/skills/_shared/gate-rendering.md` §Turn-completion guard).

**Pending-user-question check (deliberately un-numbered, like the turn-completion check).** A direct user question pending in the conversation is answered in the next assistant message — before status updates, operational gates, or new spawns. Pipeline bookkeeping never displaces a pending user question; if the full answer needs work that hasn't finished, acknowledge the question and state when the answer will come.

**Contract-scope check (deliberately un-numbered, like the two above).** Adapt a running skill's MECHANISM freely — a question asked in chat where the tool is absent, agents run in sequence where the host has no fan-out. Never drop its STEPS. Four judgments talk a run into dropping them, each sounding like good engineering: the task looks small, the host looks limited, a wrapper (a workflow, an ultracode run) looks like it supersedes the skill, or the whole thing reads as heavier than the work deserves. What gets re-classified as ceremony is the gates, the questions, and the state writes — which is what the user invoked the skill for. A skill that genuinely does not fit is one to say so about and stop, not one to keep running at reduced scope: a silently narrowed run looks exactly like a complete one, except for the state file — so a run that has edited source without writing one has already left the contract.

## Budgets — quality-first (canonical)

No hard kill caps. No wall-time, total-tool-call, total-model-turn, or total-cost ceiling — the run spends whatever the quality bar needs, and user tokens are unlimited. Bounded retry loops (invariant 5) and per-output size caps (invariant 4) still apply; those bound a single step, not the run. A skill cites this doctrine and adds only its own skill-specific gate table (e.g. a reviewer per-dimension output cap, a max-hypotheses count) rather than restating the no-hard-caps rule.

These invariants, the turn-completion check, the pending-user-question check, and the quality-first budget doctrine are skill-agnostic. A skill's own SKILL.md lists any additional invariants its workflow needs.
