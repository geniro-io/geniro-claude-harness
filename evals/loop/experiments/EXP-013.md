# EXP-013: does D4 check 9 pay for itself?

- **Module:** audit-instructions
- **Status:** blocked on the noise axis (EXP-011 / EXP-012)
- **Failure pattern:** the two audit skills rule oppositely on one text shape.
  `audit-instructions` D4 check 9 flags "the case for the rule, shipped with the
  rule" — source lists, evidence grading, refutations of a rejected theory, how
  the rule arrived. `audit-plugin`'s do-not-flag list endorses those same four
  categories, and its entry carries measured history: cutting them "was a
  dimension of its own for seven rounds and produced the provenance,
  evidence-grading and origin-narration findings that came back every time".
  One skill's measured false-positive class is the other's check.
- **Change (ONE thing):** remove check 9 from D4, and with it the two
  do-not-flag pointers that name it — a pointer at a removed check is not a
  second change, it is the same one finished.
- **Prediction:** the champion wins recall on planted-2 (gt-8 is a check-9
  defect by construction) and the variant flags less beyond the rubric. The
  question is whether the noise saved across the other four tasks is worth the
  one recall item.
- **Success gate for promotion:** noise CI upper bound below zero AND recall
  CI lower bound at or above zero. Anything else keeps the champion.

## What this can and cannot decide

**It cannot adjudicate the disagreement.** The rubric encodes the
`audit-instructions` position — planted-2 gt-8 asserts that a standalone
section arguing a rule's case is genuine bloat in a project's agent
instructions. Given that assertion, removing the check must cost recall there.
So this measures the check's *cost elsewhere*, not whether its premise is
right.

**The disagreement may not be one.** The two skills audit different targets: a
project's agent-facing instruction files versus this repo's author-facing rule
files. `rule-writing.md` binds an author writing a rule; `audit-plugin`'s entry
reasons explicitly from that scope. A rule file that argues its own case to a
future maintainer and an always-on CLAUDE.md that does the same to an executing
agent are not obviously the same artifact. What would settle it is a fixture
pair — the same paragraph in both contexts, on opposite sides of the rubric —
and that is a benchmark to build, not a run to launch.

So read a win here as "check 9 costs more noise than it returns on THIS
corpus", and a loss as "check 9 earns its place". Neither licenses editing
`audit-plugin`'s do-not-flag list.

## Blocked, and by what

EXP-011 and EXP-012 found the noise axis does not reproduce between identical
arms on either audit module. This experiment's whole benefit case is a noise
reduction, so running it now would produce a number in the range the A-vs-A
showed is indistinguishable from a coin flip.

Its cost side would still read: recall is stable, gt-8 is a must-find, and
removing check 9 should lose it. So the run as it stands can only measure what
the change costs and not what it buys — the same defect this file already names
in reverse, now for a harness reason rather than a rubric one.

Unblocks when the judge is calibrated against the `audit-findings` shape and a
re-run A-vs-A brackets zero on noise.
