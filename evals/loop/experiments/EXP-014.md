# EXP-014: does a REAL repository de-saturate the recon benchmark?

- **Module:** recon
- **Status:** landed — benchmark change only, no artifact change. **Gate NOT met:
  the benchmark is still saturated.**
- **Failure pattern:** a stand failure, inherited from EXP-011: the champion
  scored `recall_must` AND `recall_all` 1.0 on every positive task, so the recall
  MDE is 0 and the module can prove a variant did no harm but not that one
  helped.
- **Change (ONE thing):** one new dev task, `real-1`, staged from a real
  ~15k-file TypeScript monorepo at a pinned commit. No rubric on any existing
  task was touched; `variants/champion` is byte-identical to EXP-011.
- **The task itself is NOT committed.** Its ground truth was the private source
  repository's own file paths and internal identifiers, and this repository is
  public. The measurement below stands on its own — it is a recorded result, and
  run directories are gitignored regardless — but the task was withdrawn rather
  than anonymized, because anonymizing it would have broken the very thing it
  measured: the rubric matches by real path against a tree staged from that repo,
  so a renamed path matches nothing. Reproducing it means re-authoring it locally
  against a `repo_alias` in the gitignored `repos.local.json`.
- **Prediction (written before the run):** `recall_must` drops below 1.0 on
  `real-1`, driven by gt-3 — see below. Prior evidence says fixture *difficulty*
  is not the lever (nine deliberately multi-hop plants on the audit-instructions
  module were caught 20/20), and the stated reason was that the expensive hops
  live in scale, not structure. `real-1` is the direct test of that explanation:
  same multi-hop shape, but 15k files instead of six.
- **Success gate:** at least one positive task below 1.0.

## The task

A real analytics change, staged at the commit BEFORE it landed, with ground
truth read off the actual diff rather than guessed. Six of its seven items are
ordinary recon (the component to edit, the shared event registry, the analytics
hook to reuse, the matching `.claude/rules/` entry, change_scope).

gt-3 is the one built to be hard, and it is a genuine multi-hop:

1. the spec names no file at all;
2. the event is already declared in a shared package with the shape
   `{ task_id: string }`;
3. one other emitter already exists somewhere in the web app;
4. a second emitter with no discriminator merges both surfaces into one count
   that cannot be split afterwards;
5. so the new required property makes that pre-existing call site stale, and it
   must be edited too.

The spec states only the consequence ("no existing emitter is left passing a
stale payload shape") and never the file. Finding it means grepping a 15k-file
tree for the event name and reasoning about the contract.

## What this says

**The prediction was wrong, and so was the explanation it rested on.** The
existing refutation of fixture-difficulty ended with "the hops that defeat a
reviewer in a real repo are the ones it cannot afford to take — across thousands
of files, unclear ownership, absent history. A hand-built fixture cannot express
that, because the thing that makes the hop expensive is scale, not structure."
`real-1` supplied exactly that scale — 14,912 files, real ownership, real
history — and the hop was taken anyway, by BOTH tiers, one of them Sonnet.

So the corrected reading is narrower and more useful: **scale alone does not make
a recon hop expensive when the hop has a greppable anchor.** The event name is a
unique string; `grep` collapses 15k files to two call sites, and the tree size
never enters. A recon item is hard when there is no such anchor — when the
connection is nominal (a helper named nothing like the task, which `planted-5`
tests) or absent from the text entirely.

**Recall on this module is a closed axis.** Three attempts have now failed to
open it: multi-hop synthetic plants (elsewhere, 20/20), this module's own
deliberately-multi-hop dev set (EXP-011, 1.0 everywhere), and a real monorepo
with a contract-coupling item (here). The honest terminal reading is that Phase 1
recon, at either tier, does not miss what these benchmarks know how to ask for.
Effort belongs on precision and on report volume, where the arms DO differ
(23 vs 17 findings on this task; 19.7 vs 14.8 across the suite) — not on
another round of recall fixtures.

**Do not spend a fourth round on recall headroom for this module.** If a future
run needs it, the only untried lever is a task whose ground truth has no
greppable anchor at all — and `planted-5` already suggests the champion handles
that one too.

## Cost note

`real-1` staged 14,912 files. Executor spawns on it ran 62k–101k tokens against
~60k for a synthetic task, and the Sonnet explorer took 32 tool calls to the
session tier's 28 — so the real task costs roughly 1.5x a planted one on the free
subagent path, and would cost considerably more on a metered adapter. Probe
before ever running this task set on a paid executor.
