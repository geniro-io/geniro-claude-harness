State.md `phase: clarify` during this phase.

This phase is a decision-tree grill: work the design's open decisions in rounds, each round asking the whole frontier, until the branches that shape the spec resolve. A real plan is a tree of dependent decisions — resolving a parent reshapes (or removes) its children, so the question set cannot be enumerated up front.

### 3.1 Build the decision tree

Build the tree from:
- Phase 1 research findings ("found 3 auth flows — which one is the integration surface?")
- L2 query-learnings ("a prior decision favored Approach X — does it apply here?")
- L4 code-style rules

Root = the feature. Branches = its major design axes (data model, integration surface, failure handling, UX, scope edges). A child decision that only matters under a particular parent answer hangs off that parent.

**Codebase-first.** Before asking anything the code can answer, look it up — one Read for a single-file fact; for a multi-file question spawn `codebase-research-agent` (invariant S1) as **light (mid)** per `${CLAUDE_PLUGIN_ROOT}/skills/_shared/model-tiering.md` §Cost classes, in the background (Shape A of `${CLAUDE_PLUGIN_ROOT}/skills/_shared/idle-overlap.md`) and ask the rest of the frontier now: a running lookup never blocks a round, only the questions downstream of it wait, and it drains before the round that needs it. Ask only what the code cannot settle: a question answerable from L3 `_project.md` ("what test runner?") is forbidden — answer it silently and move on. The same bar applies to the user's answers: when an answer asserts how the system behaves today, verify the assertion against the code before building the tree on it, by the same lookup rule. On a contradiction, make it a question in the next round ("the code cancels whole orders at `src/orders/cancel.ts:40`, but you said partial cancellation exists — which is right?") rather than planning on the stated version. When a concept boundary stays vague after a direct question, re-ask through a concrete edge-case scenario — a specific case forces a precise answer where a repeated abstract question invites another vague one.

**Grill the scope edge, not only the design.** One branch of every tree asks whether the full scope is the right scope: which part of the request carries most of the value, what a strict subset would leave out, and whether an existing mechanism or a configuration change already meets the underlying need. A grill that only resolves *how* to build treats *whether* to build as settled by the request — and the request is what the user came here to think through. Whatever this branch resolves feeds Phase 4, where a reduced-scope shape competes as a real approach (§4.1). When it resolves the other way — the need is already met, and the honest answer is to build nothing — settle it here rather than carrying it forward as an approach: Phase 4's output becomes a spec, so there is no candidate for it to be. Confirm with the user, then run the §9.2 transient cleanup (`clean_task_transients`, `loop-phase-9-handoff.md`) and walk `loop-definition-of-done.md` §Abort-path subset, then write the terminal `phase: aborted` with a `## Termination reason` naming the conclusion. Surface it in plain English as a decision the planning reached, not a cancelled run — a plan that ends in "this does not need building" spent the grill well.

**Terminology check.** When CLAUDE.md carries a Domain Context glossary, check the topic's and each answer's domain terms against it — a plan authored with mismatched vocabulary produces a spec /geniro:implement builds wrong. On a conflict ("the glossary defines *cancellation* as void-before-capture; this answer uses it as refund-after-capture"), surface it as a grill question rather than silently picking a meaning. When a term is fuzzy or overloaded ("account" — the Customer or the User?), propose one canonical term and use it for the rest of the run. When a terminology question resolves, emit an L2 entry per `${CLAUDE_PLUGIN_ROOT}/skills/_shared/emit-learning.md` (`type: convention`, `trust: verified`, tags including `glossary` plus the task-area terms, since later reads surface an entry only by a shared tag, summary `<term> means <meaning>`) with the caller contract's echo. The readers are the Phase 1 past-learnings read here and `/geniro:implement` Phase 1 (its `knowledge-retrieval-agent` sweep); this phase never edits source.

**Grill early during the explore wait.** When the §1.2 explore agents were backgrounded, the orchestrator MAY ask the code-independent frontier early, per the same Shape A. Eligible: branches sourced from L2 learnings, L4 rules, and task-generic scope edges (feature-flag / rollout / in-scope-surface). HELD until the §1.5 drain: the Phase-1-findings-derived branch and anything L3 `_project.md` could answer — the "Codebase-first" forbidden set. Persist the early answers to `approvals[]`; Phase 3 regenerates its tree skipping answered branches (never re-ask). With no code-independent question, wait for the drain.

**Seed from the conversation.** A decision the user already settled earlier in this session is a resolved node: list it in the first round's message for confirmation instead of asking it again; a correction reopens the node as a question.

**Walk by rounds.** The frontier is every open decision whose prerequisites are settled. A question that depends on another question still open in this round waits for a later round. After each round, recompute the frontier from the answers: a settled parent unblocks its children and can moot others (drop them).

### 3.2 AUQ shape — message-first, one round at a time

Apply the Gate presentation contract. Render the round to a chat message first, as a numbered list of its questions, each framed and carrying its recommended answer — the user is confirming a default, not authoring from scratch. Size each framing to its question: a one-line orientation when every option is self-explanatory, or — when an option's consequence needs more than its one-line `description` — a short per-option consequence block in the two layers of `${CLAUDE_PLUGIN_ROOT}/skills/_shared/gate-rendering.md` §Two explanation layers: what the user would end up with under that option, in ordinary words, then a `**Technical detail:**` line carrying the code anchor, config diff, or behavior trace. A consequence block that opens on a diff answers a question the user has not been able to form yet. Then fire the lean AUQ: one `AskUserQuestion` call carries up to 4 of the round's questions (the tool's per-call cap); a larger round chains further calls from the same message, and the round's answers are all in before the next round starts. Short labels + one-line `description`s, Recommended-first.

Each round's answers reshape the frontier — a still-pending child can become moot (drop it) or need reworded options — so do NOT pre-generate beyond the current round; regenerate from the live tree. Each question uses a `header` per the Gate presentation contract's cap, a `question` of 1-2 sentences ending in a question mark, `options[]` of 2-4 explicit choices, and `multiSelect: false` unless explicitly multi-select. Include a "Skip — proceed with stated assumption" option as the last choice when applicable. When the decision may not be the user's to make (policy, budget, another team's interface), also offer "Someone else decides this" — at the 4-option cap, drop Skip first. That pick opens one follow-up for the owner's name (role options the conversation already named; the user types a name via Other) and records `picked: "pending: <owner>"` (quoted, as YAML requires). A project that wants one question at a time says so in a loaded custom instruction; each round is then the single highest-leverage frontier question. The grill is uncapped but bounded by the §3.4 checkpoint gate. Full literal example with the round message + AUQ in `${CLAUDE_PLUGIN_ROOT}/skills/plan/plan-auq-reference.md` §2.

### 3.3 Persistence

Each answered question → append entry to state.md frontmatter `approvals[]` via `atomic_state_append_list_item`. Append the `approvals[]` entry for each answer before rendering the next round — so a context reset mid-sequence preserves every answer already given; on a compaction-resume, re-read `approvals[]` and skip the questions already answered. Entry shape in `${CLAUDE_PLUGIN_ROOT}/skills/plan/plan-auq-reference.md` §1; category `clarify_<dim>`.

### 3.4 Checkpoint gate and termination

There is no fixed question cap — the grill runs until the spec-shaping branches resolve. To keep it bounded, pause for a checkpoint whichever comes first: a full design branch resolves, 2 rounds have run since the last checkpoint, OR the answers start signalling convergence — replies shortening to a word where earlier ones were considered, "just pick one", a question waved away rather than answered. That last trigger is the one a fixed cadence cannot see: a user who has stopped engaging answers the next four questions as fast as the first, and the cadence reads that speed as progress. This is an escalation gate, not an abort — the user, not a fixed number, decides when to stop.

**Artifact** — fire the before-gate update for this site (call-site table in `loop-artifact-call-sites.md`) before the checkpoint AUQ and before the exit AUQ below.

At a checkpoint, render a running summary to a chat message — resolved decisions, deferred items, and the open branches still to walk — then fire ONE lean AUQ:
- **Keep grilling** (Recommended while open branches remain) — continue the walk.
- **Wrap up now** — stop; remaining open branches become stated assumptions.
- **Skip remaining branches with stated assumptions** — same as wrap-up, but name the skipped branches explicitly in the Assumptions section for /geniro:implement to verify.

Persist each checkpoint decision to `approvals[]` category `grill_checkpoint` via `atomic_state_append_list_item` before continuing.

**Termination** fires when the user picks Wrap up / Skip at a checkpoint, or when the branches resolve and no spec-shaping question remains. On termination, render a closing summary — resolved decisions, deferred work, and any unaddressed risks — and hold it in context: it feeds Phase 4 approach generation and seeds Phase 5 sections (Steps / Validation / Done Condition). When any branch closed `pending: <owner>`, also write `<task-dir>/questionnaire.md` via `atomic_state_write` — one section per owner, each question carrying its context (why it matters, what the code shows), the options considered with the recommended one marked, and an empty answer stub.

**The exit is gated — the grill never ends on the model's own judgment.** When termination comes from an exhausted tree rather than a user pick, fire ONE lean AUQ after the closing summary and before Phase 4: start building / keep grilling deeper / keep grilling on an area the user names. "Nothing left to ask" is the model's read of a tree it built itself, and a run that resolved two branches in two questions looks exhausted from the inside — so **keep grilling stays live with an empty frontier**. On the deeper pick, open a second pass over the angles a first walk routinely leaves closed (failure and rollback behavior, operational surface, data migration and backfill, the scope edges that were assumed rather than decided) rather than re-asking what resolved. On the named-area pick, the next question IS that grill question — offer the candidate angles as its options, with the user free to name their own, then build the branch from the answer and walk it by rounds per §3.1. Either way the walk resumes and terminates again: this gate re-fires at every termination, uncapped. Skip it only when the user picked Wrap up / Skip at a checkpoint — that pick already is this decision, and re-asking it reads as not having listened. Persist the pick to `approvals[]` category `grill_checkpoint` via `atomic_state_append_list_item`.

**Every branch that closes without an answer becomes a written assumption.** Carry each one into the closing summary as a checkable predicate about the code or the environment — "the `users` table has a `deleted_at` column", not "auth is handled elsewhere" — and hold that list for Phase 5 to author into spec section 4; a `pending: <owner>` branch carries over as `pending: <owner> — <decision>; working assumption: <the recommended answer>` instead, since a decision is not a code predicate. A branch left open is a decision the plan makes silently, and an unwritten one is invisible to every gate that follows: the Phase 7.5 challenge verifies section 4 assumptions claim by claim against the code, so a predicate written down gets checked and one kept in context does not. Then transition to Phase 4. The checkpoint and termination summary templates are in `${CLAUDE_PLUGIN_ROOT}/skills/plan/plan-auq-reference.md` §2.

**Artifact** — on termination, fire the update for this site (call-site table in `loop-artifact-call-sites.md`).
