# EXP-019: does decomposing cross-location reliances into one agent per obligation reach the callee-contract misses that prose and a required slot could not?

- **Module:** review
- **Status:** **REJECTED at Gate 0**, 2026-08-12. The original PASS was produced at
  session tier with an uncapped budget; re-run on the screening executor in a facet's
  envelope it FAILS both pre-registered criteria. See §Gate 0 re-run — and read that
  section before reading the original §Gate 0 result below, which it supersedes.
- **Failure pattern:** the EXP-002 / EXP-005 residual. Three of the five systematic
  dev misses share one shape: the defect lives in the CONTRACT OF CODE THE DIFF
  CALLS, not in the diff text. `real-4` gt-1 — an awaited upload callee throws on
  non-2xx, so a rejection skips both reset branches and leaves `isUploading` stuck.
  `real-5` gt-2 — a UI surface is exposed to a role whose backing endpoint is
  admin-only and 403s. `real-5` gt-4 — a shared MultiSelect's implicit
  bulk-deselect surfaces revoke access in one click. Two interventions have already
  failed on exactly these items: EXP-002 made the callee-contract read mandatory in
  prose (+0.036, CI [0, 0.107] — gate not met) and EXP-005 made it a REQUIRED output
  slot (exact tie). EXP-005's autopsy is the reason to try a third time with a
  different mechanism rather than a fourth wording: the reviewer reads callee
  contracts ONE hop deep even when forced to enumerate them. Both prior attempts
  changed what the reviewer was TOLD while leaving one agent facing every reliance
  at once.
- **Change (ONE thing):** structure, not wording. A pre-finding stage extracts the
  cross-location reliances the diff introduces — each shaped `{where, relies_on,
  property}` — and then spawns ONE agent per reliance to read BOTH ends and return
  whether the property holds. Failed obligations enter the pipeline as ordinary
  finding candidates BEFORE the admission gate, so they are verified and severity-
  scored like any other finding rather than bypassing either.
- **Prediction:** Δrecall_must **+0.026 to +0.079** on dev-19, most likely
  **+0.039** (`real-4` gt-1 and `real-5` gt-2 unlocking; one real-4 must-item =
  0.5/19 = 0.026, one real-5 must-item = 0.25/19 = 0.013). Δnoise_strict +0 to
  +1.0/task. **Pre-registered power caveat: the most likely effect is BELOW the
  detection floor.** MDE on this stand is 0.054 (EXP-001/002) to 0.071 (EXP-004), so
  a genuine 1-2 item unlock reads as a tie. Only >=3 must-unlocks reproduced in both
  trials clears CI > 0. Any screen is therefore a bet that the effect is larger than
  predicted, and a tie will NOT distinguish "mechanism does not work" from "stand
  cannot see it".
- **Success gate:** staged, cheapest-kill-first.
  - **Gate 0 — extraction probe (~$0, Claude subagents, no judge).** Run extraction
    alone on `real-4` and `real-5`. PASS requires the emitted reliance for `real-4`
    to name the callee's REJECTION PATH as the relied-on property (can it throw /
    reject), and for `real-5` to name WHO IS AUTHORIZED to call the endpoint.
    Naming the callee while describing its return shape is a FAIL — that is exactly
    EXP-005's residual, and the whole mechanism rests on the property being the
    right one. A fail kills the hypothesis for nothing.
  - **Gate 1 — mini-screen (~$9):** 4 target-class tasks + `planted-neg-1` as the
    noise sentinel, obligation stage only, champion arm replayed from cache. Any new
    must-unlock with sane noise proceeds; zero movement rejects.
  - **Gate 2 — full dev-19 screen, 2 trials:** Δrecall_must CI > 0 with noise not
    significantly worse.
  - **Gate 3 — holdout + second family.** Plus the sampling control EXP-004 never
    ran: an arm with N identical obligation agents over the SAME reliance list, to
    separate decomposition from extra draws.

## Expressibility — blocks Gate 1, not Gate 0

The stand cannot express this variant as a variant directory. Facet count is static
from `facets.json`, each facet's prompt is assembled once with no channel from
another facet's output, and facets fire into a flat dependency-free pool. Union
scoring across facets exists; a dependent, dynamically-sized second stage does not.
Gate 1 therefore needs harness work first: `depends_on` + `fanout` in `facets.json`,
a `scored: false` flag for stage-1 output (otherwise the parser reads stage-1's
`### ` blocks as findings and the retry regex retries a valid stage-1 emit), and a
`--probe` fix, since probe extrapolates from `N_FACETS x tasks x trials` and a
dynamic fan-out leaves `--max-usd` as the only live guard. Note also that a stage-1
cache miss invalidates that task's whole stage-2 fan-out, so re-runs are not free.

Gate 0 needs none of that — it runs the extraction prompt directly and is read by
hand.

## Cost, if it ever ships

Measured per-call units from `screen19-exp002-t1`: ~2.34M in, ~11.1K out, ~$0.33 per
agentic call. On a typical PR (8 dims, 8 survivors, 3 verifier clusters = 11 spawns):
one-agent-per-obligation at N=12 is 25 spawns (+127%, ~+115% tokens) — roughly 4x the
cells and 2x the output of EXP-004, the only intervention that ever measured positive
here, for an unmeasured effect. Grouping obligations by target file at the existing
same-file cluster cap of 3 gives 17 spawns (+55%) — the only same-order configuration,
and the one to screen. Grouping may also blunt the single mechanism being tested
(narrow scope forcing the multi-hop trace), which is what the Gate 3 control settles.

## Architectural constraints any implementation must satisfy

Recorded here because they bound the design, not as a result:

- The bound is on SPAWNS, derived and echoed at fire time — not a bare integer in a
  prompt. The sanctioned per-item spawn classes (per-finding verifiers, deep-mode
  angles) are all bounded by an upstream gate the user consented to, with a derived
  count declared before firing; the 33-spawn incident is what an undeclared
  content-scaled multiplier looks like.
- The declared-vs-actual spawn gate must exclude this fan-out from its reviewer-spawn
  comparison, as it already does for deep-mode angles, or its over-fire branch fires
  every run.
- The orchestrator fans out, never the extraction agent — subagents cannot spawn
  sub-tasks.
- Opt-in under `--deep` only: the cost is about one extra reviewer batch, which is
  the standing argument for opt-in, and EXP-004 showed deep's gain on these exact
  tasks is pass@k-shaped rather than deterministic.

## Gate 0 result

Extraction alone, no verification stage, no judge, read by hand. Prompt asked only for
`{where, relies_on, property}` triples with the property stated as a checkable
condition; it named no defect class, so nothing steered it toward throwing or authz.

**`real-5` — PASS, and more than the gate asked.** The extraction surfaced all FOUR
must-find items as reliances, each with the property framed correctly:

- gt-2 (the gate's own criterion) — named `GET /users/list`'s `RolesGuard(Admin)` as the
  relied-on code and the property as *"the endpoint must be callable by the sessions this
  query is enabled for … admits only session role exactly `admin` … so a beneficiary's
  candidate list is non-empty only if a non-admin session is authorized here."* That is
  the authorization property, not the return shape.
- gt-1 — the dropped server-side search: *"every user who could be added must fall inside
  the 50 most-recently-created … the component's own filter can only narrow that one
  page — it can never reach a candidate outside it."*
- gt-3 — the removed beneficiary gate: *"TeamSection must render nothing a beneficiary is
  forbidden to see … the beneficiary now sees exactly what internal staff see."*
- gt-4 — the implicit bulk-deselect: *"a single click can drop every contributor, or every
  contributor past the third … so a one-click bulk removal must be intended semantics."*

The champion reviewer missed gt-2 and gt-4 deterministically in BOTH trials of EXP-002.
Reliance-shaped extraction reached them without being told what to look for.

**`real-4` — MISS on gt-1.** No reliance named the upload callee's rejection path. The
awaited `onFileUpload` / `filesGetFileStatus` pair, which throws on non-2xx and leaves
`isUploading` stuck, does not appear among the 14 emitted rows; the closest row cites the
same upload utility but frames its property as UUID canonicality instead.

Notably the SHAPE was available: an unprompted row states of the analytics call *"the
returned promise must always resolve, never reject … these are floating promises, so a
rejection surfaces as an unhandled rejection rather than being caught by the upload
handler."* So framing a reliance as a rejection path is within reach; on this task it
landed on the wrong callee. The residual is salience selection, not vocabulary.

**Confounds — do not read this as a screen.** Executor was a Claude subagent at the
session tier with an uncapped turn budget; the two probes spent 55 and 77 tool calls,
far more reading than a production reviewer facet gets. A per-obligation agent in the real
pipeline is narrow BY CONSTRUCTION, which is the mechanism's claim, but this probe did not
test it under a facet's compute envelope, and it used a different executor family from the
screening tier. It also measured extraction only — the verify half that decides `holds`
was not run, and neither was noise.

**What it changes:** Gate 0's premise question is answered yes — reliance-shaped
extraction with the property as the unit does surface contract defects a monolithic
reviewer missed, on 4 of 5 target must-items. The hypothesis is alive and worth the
harness work. It does NOT establish the effect survives a narrower envelope, a cheaper
executor, or the noise axis, and the §Prediction power caveat stands unchanged: even a
working mechanism most likely reads as a tie on dev-19.

## Gate 0 re-run — screening executor, facet envelope

The §Gate 0 result above carries its own instruction to re-run before spending. This is
that re-run, and it reverses the verdict.

**What was held fixed:** the extraction instructions, byte-identical to the original
probe. **What changed, deliberately two things:** the executor (session-tier Claude
subagent → `composer-2.5`, the designed screening tier) and the delivery envelope (live
repo with free `git` access and 55-77 tool calls → one shot through
`adapters/cursor-cli.sh`, workspace = staged worktree, diff inline, full content of
changed files, as `run.sh` assembles it for a production facet). Both were named as
confounds in the original result, so both had to go; that does mean a MISS does not
isolate which one caused it. 2 trials per task, 4 calls total.

**Result — FAIL on both pre-registered criteria.**

| task | trial | rows | gate criterion | verdict |
|---|---|---|---|---|
| real-4 | 1 | 14 | property names the callee's rejection path | **FAIL** — `:150` row present, property is *"`onFileUpload(file)` returns a non-null `fileId` … otherwise upload handlers reset UI state"* |
| real-4 | 2 | 14 | " | **FAIL** — `:151` row, *"must return a non-null `fileId` from `uploadFile`"* |
| real-5 | 1 | 14 | property names who is authorized to call the endpoint | **FAIL** — no row mentions `users/list`, admin-only, 403, or `RolesGuard`; gt-3 hit, gt-1/gt-2/gt-4 missed |
| real-5 | 2 | 14 | " | **FAIL** — same; gt-1 hit, gt-2/gt-3/gt-4 missed |

`real-4` gt-1 is now missed by 3 of 3 probes across both executor families, always with
the same return-shape framing. Trial-1's property is worse than a miss: *"otherwise
upload handlers reset UI state"* asserts as holding the exact assumption the defect
violates — on a throw, neither reset branch runs. Zero promise-rejection vocabulary
appears anywhere in either `real-4` trial (the single "reject" hit is MIME validation).

`real-5` collapses from 4/4 at session tier to **1/4 per trial, and not the same item
twice** (union 2/4: gt-1 in trial-2, gt-3 in trial-1). gt-2, the gate's own criterion,
misses in both.

**The decisive cell is `real-5` trial-2, and it is a structural finding, not a miss.**
One row's `where` spans `manage-team-panel.tsx:127-133,370-373` — including gt-2's exact
line 133 — and its `relies_on` cites `apps/api/src/user/controllers/user.controller.ts:41`,
the candidate endpoint itself. In the staged tree, `@UseGuards(RolesGuard(UserRole.Admin))`
sits three lines above that citation and the literal string `List all users (admin only)`
two lines above. The extractor read the file, cited the line, and selected **pagination**
as the property. The miss is property SELECTION, not code discovery.

That is what kills the mechanism rather than merely failing it. Stage 2 verifies the
property stage 1 chose. If stage 1 picks "returns a non-null fileId" or "returns a
paginated list", a fresh narrow-scope agent will faithfully confirm that property holds —
and the rejection path and the admin guard are never examined by anything. Decomposition
inherits stage-1 property selection; it cannot repair it. The hypothesis was that narrow
scope forces the multi-hop trace, but the scope gets narrowed around the wrong property.
This is EXP-005's residual reappearing one stage earlier, which is precisely where
decomposition has no purchase.

**Cost — I under-estimated by 7.7x and it is worth recording.** Predicted ~$0.20 from the
`$0.0486`/call figure; **measured $1.54** (harness formula, `run.sh:171`: `inputTokens +
cacheReadTokens + outputTokens` x `$0.22`/Mtok). Per-call totals were 1.3M-2.1M tokens,
dominated by 1.2M-2.0M cache-read. The `$0.0486` unit was probed on planted synthetic
tasks at ~11.6K input tokens per call; a `real-*` monorepo task with tree-walking runs
~13x that. **Do not price a `real-*` task from a `planted-*` probe** — budget ~$0.35-0.50
per real-task agentic call.

**What this does not establish.** Two variables moved at once, so "the mechanism works at
session tier but not at screening tier" remains formally consistent with these four calls.
It is not a useful escape: the stand screens and promotes on the screening tier, so a
mechanism that needs session tier and 55-77 tool calls cannot be measured or shipped by
this harness regardless of whether it "works". The re-run also still measures extraction
only — the verify half and the noise axis were not exercised, and now never will be.

## Decision

**REJECTED at Gate 0, 2026-08-12.** Pre-registered rule was "FAIL on either criterion =
REJECT, a fail kills the hypothesis for nothing" — both failed. The original PASS is
reclassified as an artifact of the session-tier executor and its uncapped budget, which is
exactly the risk that instruction to re-run was written to catch.

**Not spent, by this result:** the `depends_on` / `fanout` / `scored: false` / `--probe`
harness work, the ~$9 Gate 1 mini-screen, and the full dev-19 Gate 2 screen whose
pre-registered power caveat already said a 1-2 item unlock would read as a tie. Total cost
of the kill: $1.54.

**Do not re-propose obligation decomposition on the strength of the original real-5 4/4.**
Any future attempt at this defect class must first show that property SELECTION improves —
that the extractor names the rejection path and the authorization guard when it is looking
at them — because every mechanism downstream of extraction inherits whatever property
stage 1 picked. Three interventions (EXP-002 prose, EXP-005 required slot, EXP-019
decomposition) have now failed on the same three items, and this run is the first to
localize why.
